# Updating itself

Shiro updates from the `dev` release on GitHub. This is how that works, and the
one step that is not automated because it must not be.

---

## 0. The short version

1. **CI stamps a version.** `0.1.<run number>`, at build time, not in the repo -
   so every build published from `main` is strictly newer than the last, which
   is the only reason "is there an update" has an answer. Both platforms take
   the number from the same run, so they cannot disagree about what they built.
2. **The update is signed, and the signature is the security.** The download is
   a public release asset over HTTPS; anybody can serve a copy of that URL. What
   they cannot do is sign it with a key we hold, and the app refuses anything
   whose signature does not match the public key in `tauri.conf.json`.
3. **Nothing installs itself.** The app checks a few seconds after start, says
   so quietly beside the version, and does nothing else until asked. Restarting
   is a second, separate press.
4. **One manual step, once:** the private key has to be added to the repository
   secrets. Until it is, builds still publish an installer, and autoupdate stays
   on whatever the previous build was. §3.

---

## 1. Why the version has to move

The updater compares the running version with the one in `latest.json`. Every
build was `0.1.0`, so nothing was ever newer and nothing would ever update.

CI stamps `0.1.<github.run_number>` into `tauri.conf.json` and `package.json`
immediately before building, on pushes to `main` only. The run number only ever
increases for a workflow, which is exactly the property needed. It is stamped
rather than committed so `main` stays on the base version and there is no
version-bump commit in the history.

A pull request build is never published, so it is not renumbered - the artifact
would just be confusingly labelled.

The app shows the version it actually is, read from the binary with
`getVersion()`. A number written into the UI is a number that was true once.

---

## 2. Why `createUpdaterArtifacts` is not in the config

It is in `src-tauri/updater.json`, applied by CI with `--config` on the one path
that has a signing key.

With the flag on and no private key, the bundler does not warn - it **fails**:

```
A public key has been found, but no private key.
Make sure to set `TAURI_SIGNING_PRIVATE_KEY` environment variable.
```

That was measured, not assumed. In the committed config it would break every
pull request build, every fork, and every developer without the secret. So the
build step turns updater artifacts on only when a key is present, and says which
of the two it did.

---

## 3. The one manual step

The private key is not in this repository and must never be. To finish the setup:

```bash
npx tauri signer generate -w ~/.shiro-updater.key
```

Then add two repository secrets - Settings, Secrets and variables, Actions:

| secret | value |
|---|---|
| `TAURI_SIGNING_PRIVATE_KEY` | the contents of the private key file |
| `TAURI_SIGNING_PRIVATE_KEY_PASSWORD` | the password, or empty if none |

and put the **public** half in `tauri.conf.json` under `plugins.updater.pubkey`.

**Keep the private key.** Losing it means no existing installation can ever
update again: they will each reject a build signed with a new key, exactly as
they are supposed to, and everyone has to reinstall by hand.

Until the secrets exist, the workflow publishes the installer and logs
`No signing key - building the installer only.` Autoupdate simply does not
advance, which is the right failure: an unsigned update is one the app would
refuse anyway, and publishing a manifest pointing at it would strand people on
a broken check.

## 3a. Linux

The same release carries the deb, the rpm and the AppImage, all stamped with the
same version as the Windows build - they used to all claim `0.1.0`, which meant
`apt` considered a newer one already installed.

**Only the AppImage self-updates.** It is the one Tauri can replace in place;
deb and rpm are managed by the system package manager and Shiro has no business
writing to `/usr/bin`. So a deb or rpm install checks, finds a newer version,
and can tell you about it - but installing it is `apt install` by hand.

Both platforms are built by one workflow, and one job publishes both. That is
not tidiness: there is a single `latest.json`, and two workflows writing it
would race, with the loser's platform silently missing from the manifest.

`linux-build.yml` still exists and is the pull request check.

## 4. The channel

`https://github.com/QrowZK/shiro/releases/download/dev/latest.json`

The tag is named because GitHub's `/releases/latest` **ignores prereleases**,
and `dev` is one. The assets are replaced on every push to `main`, so the URL is
stable and always describes the newest build.

`latest.json` is generated by the publish step and carries the version, the
notes, the download URL and the signature. It is only written when a `.sig`
exists beside the installer - see §3.

The signed artifact **is the installer**. For NSIS, Tauri v2 signs
`Shiro_<version>_x64-setup.exe` and writes `.exe.sig` next to it; the app
downloads that same `.exe`. There is no `.nsis.zip` - that was v1, and looking
for one is why the first signed build published no manifest at all.

Moving to real releases later means changing the endpoint and the publish step,
and nothing else: the app does not know what a channel is.

---

## 5. What it does to the person using it

- A check runs four seconds after start, once per session. Not on a timer, and
  not while logging in.
- An available update shows as a mark beside the version in the title bar and a
  button in Settings. There is no dialog: an update prompt over a battle is an
  interruption, and this is never urgent enough to earn one.
- Downloading reports a percentage when the server sends a length, and says
  "Downloading…" when it does not, rather than inventing one.
- The new build applies on restart, and the restart is the player's press. An
  update that closes the app mid-game is worse than an update that waits.
- A failed check is reported in Settings and nowhere else. It is the least
  important thing the app does.

---

## 6. What not to do

- **Do not commit the private key**, or paste it into an issue, a log, or a
  chat. It is the one secret that matters here.
- **Do not put `createUpdaterArtifacts` back in `tauri.conf.json`.** See §2.
- **Do not add an auto-install-on-quit.** The app is a lobby: people leave it
  running for hours and alt-tab into a game. Replacing the binary under them is
  not a convenience.
- **Do not check on a timer.** Once a session answers the question, and the
  endpoint is somebody else's bandwidth.
